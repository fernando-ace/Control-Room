# CR-03: Reconnect and recovery UX polish

## Objective and context

Help players understand temporary disconnects, reconnecting, crew-member availability, resynchronization, and unrecoverable mission state. Inspect current polling, Realtime, identity persistence, and UI behavior first.

## Dependencies

None. Coordinate with CR-02 and CR-07 because they may touch the same UI surfaces.

## Invariants

The server is authoritative. Preserve anonymous session identity, station ownership, membership checks, Supabase Realtime plus reconciliation, historical mission evaluation, privacy boundaries, and retry semantics. A client must never resume a seat by submitting an identity or state.

## Scope

Improve connection and resync status, explain crew disconnects and recovery, and make genuinely unrecoverable conditions understandable with safe next steps. Keep transient failures distinct from server-rejected actions and mission outcomes.

## Non-goals

Do not weaken membership/security checks, change reconnect identity semantics, add background mission processing, or change mission rules.

Do not modify `ROADMAP.json`, other goal prompts, goal CLI scripts, or workflow documentation as part of this feature.

## Definition of done

- Players can distinguish offline, reconnecting, synchronized, and terminal/recovery-needed states.
- UI recovers from transient transport failure without duplicating actions or claiming false success.
- Tests cover meaningful recovery transitions and retain authority/privacy assertions.

## Validation and completion

Inspect the implementation and tests; do not assume filenames. Run lint, typecheck, unit/API tests, build, and relevant browser/live multiplayer validation if available; run `git diff --check`. Do not weaken assertions. If acceptance cannot honestly be met, report incomplete. Review and commit locally; do not push or deploy.
