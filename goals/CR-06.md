# CR-06: Deterministic emergency variation

## Objective and context

Make repeated missions less predictable with controlled emergency variation while retaining reproducibility and rigorous tests. Inspect mission seeding, persistence, and event timing first.

## Dependencies

CR-01. The multi-mission architecture must be integrated before variation is added.

## Invariants

Variation is selected and evaluated by the server. Persist enough seed/variant data for deterministic replay after reconnect. Preserve mission deadlines, server authority, privacy, CAS semantics, and all existing Solar Storm safety guarantees.

## Scope

Add a small bounded set of balanced emergency variants, explicit deterministic selection, and tests for repeatability and valid timing/role constraints.

## Non-goals

Do not use client randomness, unbounded procedural generation, hidden test-only shortcuts, or alter existing mission difficulty guarantees without evidence.

## Definition of done

- Same stored seed and state produce the same emergency sequence.
- Different variants remain solvable and require cooperative role information.
- Reconnect, retry, and concurrent actions preserve the selected variant correctly.
- Tests cover all variants and retain existing timing/privacy checks.

## Validation and completion

Inspect current engine, persistence, and tests; do not assume filenames. Run lint, typecheck, unit/API tests, build, relevant live validation where available, and `git diff --check`. Do not weaken assertions. If acceptance is unmet, report incomplete. Review and commit locally; do not push or deploy.
