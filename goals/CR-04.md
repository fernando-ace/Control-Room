# CR-04: Post-game crew performance breakdown

## Objective and context

Show a useful cooperative account of what happened during a completed mission, grounded in real authoritative mission data. The existing mission engine owns outcomes and timestamps; inspect its current state model before designing the summary.

## Dependencies

CR-01. Do not start until mission identity/configuration has been integrated.

## Invariants

Use real server-derived mission data; never invent display-only metrics or accept client-submitted results. Preserve role-private information, three-player cooperative framing, authoritative time/outcomes, and retry behavior.

## Scope

Summarize meaningful team events, objective timing/completion, outcome, and useful improvement cues when supported by actual state. Avoid individual competitive scoring.

## Non-goals

Do not add persistent progression, analytics services, fabricated histories, new mission rules, or changes to Supabase security.

## Definition of done

- Victory and defeat show accurate, comprehensible cooperative summaries.
- Every displayed value can be traced to authoritative mission data.
- Retry cleanly starts a new run and does not contaminate the previous summary.
- Tests cover summary correctness and privacy.

## Validation and completion

Inspect implementation and tests before editing. Run lint, typecheck, unit/API tests, build, relevant browser/live validation where available, and `git diff --check`. Preserve assertions. If acceptance is not met, report incomplete. Review and commit locally; do not push or deploy.
